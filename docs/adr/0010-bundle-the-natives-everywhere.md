# ADR-0010 — Bundle the natives in every ecosystem; downloading is the fallback

- **Status:** accepted
- **Date:** 2026-08-17
- **Supersedes:** the Go section of [ADR-0007](0007-how-natives-reach-each-ecosystem.md).
  The Python and JavaScript decisions there stand unchanged.
- **Evidence:** [spike 0009](../../spikes/0009-bundle-natives/)

## Context

ADR-0007 gave each ecosystem a different mechanism: Python bundles in wheels, JS bundles
in `optionalDependencies`, and **Go downloads at runtime** from the tag-keyed natives
release. The Go exception was justified on size — five platforms inside a Go module is
~70 MB pulled by every `go get`, and `go:embed` selects at compile time, not fetch time.

That reasoning is still true. What changed is the weight put on the other side of it.

A runtime download moves failure from install-time to run-time, and run-time is where
nobody is watching. It breaks Docker layer caching, because the library is no longer in
the image the install layer produced. It breaks `pip download` / vendored offline
installs, which is precisely the enterprise that most wants an in-process model and no
daemon. It sits outside the provenance chain that `NPM_CONFIG_PROVENANCE` and PyPI
attestations already give the published artifact. And it makes a GitHub release
load-bearing at runtime for every user, subject to unauthenticated rate limits that a
CI fleet behind one NAT will hit.

The owner's call, given the tradeoff stated in megabytes: **bundle, even though it is
big.**

## Decision

**A binding carries its native closure. Downloading is a fallback, not the happy path.**

Concretely:

- **Python** — unchanged. Platform wheels, natives at `modelnexus/native/<platform>/`.
- **JavaScript** — unchanged. One package per platform plus a launcher listing them in
  `optionalDependencies`.
- **Go** — a new, **separate, opt-in module**:

  ```go
  import _ "github.com/muthuishere/modelnexus/natives"   // no network, ever
  ```

### Why a separate module rather than `bindings/go`

Go has no optional dependencies and no fetch-time selection. Natives inside
`bindings/go` means every consumer downloads ~70 MB, including the ones who only ever
set `MODELNEXUS_LIB` or ship their own build. That is a tax on the majority to serve a
minority.

A build tag does not help, and this repo already learned that: `source.go:199` puts the
S3 resolver in a separate module with the note that **a tagged file's imports still land
in `go.mod`**. Same reasoning, same shape. The base binding stays lean; the bundle is
one import away for anyone who wants a hermetic build, and they are the ones who
accepted the 70 MB by asking for it.

### Resolution order — identical in all three bindings

This is the part that makes it a specification rather than three implementations:

1. `MODELNEXUS_LIB` — explicit path, wins over everything.
2. The **bundled** closure — wheel, npm platform package, or the Go `natives` module.
   No network.
3. The repo's `core/dist/<platform>/`, for working in the tree.
4. `Fetch()` — download from the tag-keyed release into the user cache.

Today only Go has steps 3 and 4, and only Python/JS have step 2. After this, all three
have all four, and the parity gate proves they agree.

Step 4 stays because it is the escape hatch for a platform we do not build, a user
pinning a different llama.cpp, and an air-gapped mirror. Removing it would trade one
rigidity for another.

### `go:embed` destroys the closure unless the links are carried separately

Spike 0009 found this and it is the reason this ADR exists rather than a one-line
change. `dist/` is 12 regular files and **18 symlinks**, because llama.cpp ships
`libfoo.dylib -> libfoo.0.dylib -> libfoo.0.13.0.dylib` and `build.sh` preserves them
deliberately — dereferencing triples the largest library.

`go:embed` takes regular files only. It does not record symlinks and **does not error
about them.** The bridge links `@rpath/libllama.0.dylib` — a symlink. So a naive embed
produces a directory that looks complete, weighs about right, and cannot load.

Therefore: **the build generates a `links.json` manifest, and extraction replays it.**
Generated by the build, so it cannot drift from what shipped. Dereferencing instead
(~14 MB → ~40 MB per platform) is rejected on the same grounds `build.sh` already
rejects it.

Extraction is atomic — temp directory, then rename — so a killed process cannot leave a
half-extracted closure for the next run to `dlopen`. The cache directory is keyed on a
**hash of the embedded bytes**, not a version string, because keying on the llama.cpp
tag alone already served a stale library once.

### Intel macOS is built, not seeded by hand

ADR-0007 accepted `darwin-x86_64` as hand-seeded because GitHub's Intel runners queue
indefinitely. In practice that means absent: `natives-b9371` has four assets.

Bundling makes an absent platform fail at import rather than at install, so this stops
being tolerable. Spike 0009 shows it is also unnecessary. `build.sh` never compiles
llama.cpp — it downloads upstream's `macos-x64` dylibs and compiles only our ~890-line
bridge — so `-DCMAKE_OSX_ARCHITECTURES=x86_64` on the **arm64** runner produces a native
that loads and generates correctly under Rosetta. No Intel runner, no manual step.

**`linux-aarch64` is a separate hole.** ADR-0007's context claims linux x64/arm64, but
it appears in neither the build matrix nor the release loop. ARM Linux is most cloud
instances now. Not decided here — it needs its own decision rather than being smuggled
in as a matrix row.

## Consequences

- **A Go consumer who wants bundling adds one import and pays ~70 MB in the module
  cache.** One who does not, pays nothing and behaves exactly as today. Nothing about
  the existing Go API changes.
- **"Bundled" means no network, not no filesystem.** The closure is extracted to a user
  cache before loading, because a shared library cannot be portably loaded from memory.
  A read-only home directory is a real failure mode and needs a typed error naming the
  directory it tried.
- The natives release stays durable and load-bearing for step 4, exactly as ADR-0007
  said. This narrows who depends on it; it does not remove the dependency.
- **Five platforms staged instead of four.** `darwin-x86_64` joins the matrix and the
  manual seeding one-liner leaves `PUBLISHING.md`.
- The parity gate grows a case it does not have: all three bindings resolve the library
  through the same four steps in the same order. Without that, this is three
  implementations of a vibe.
- More bytes move on every release. That is the cost the owner accepted explicitly, and
  it buys install-time failure, cache-friendly containers, offline installs, and
  provenance that covers the binary a user actually loads.

## Alternatives rejected

- **Runtime download everywhere** — the symmetric option. Rejected on the grounds in
  Context: it makes the common case worse to make the rare case uniform.
- **Natives inside `bindings/go`** — ~70 MB for every consumer, including those who
  never load a bundled library.
- **A build tag instead of a separate module** — does not work in Go; the imports land
  in `go.mod` regardless. Already settled for S3 (`source.go:199`).
- **Dereference symlinks before embedding** — correct and wasteful; ~40 MB per platform.
- **Reconstruct symlinks by pattern at extract time** — guessing at a linker contract.
