## What is actually published today

| ecosystem | state |
|---|---|
| Go | **Published.** `@v0.1.0` resolves from the public proxy; inference verified from outside the repo. |
| npm | **Not published.** The workflow is wired and the tarballs were packed and installed locally; the publish leg fails on `ENEEDAUTH`. |
| PyPI | **Not published.** OIDC token is valid; PyPI has no publisher registered to match it yet. |

`PUBLISHING.md` in the repo is the current truth. Until npm and PyPI land, install the
Python and JS bindings from a checkout and point them at a local build — see
[MODELNEXUS_LIB](#modelnexus_lib) below.

## The native library

Three ways it reaches you, one per ecosystem ([ADR-0007](https://github.com/muthuishere/modelnexus/blob/main/docs/adr/0007-how-natives-reach-each-ecosystem.md)):

| | how |
|---|---|
| Python | inside the wheel |
| JavaScript | a separate per-platform package, pulled in by `optionalDependencies`, so npm installs only the one that matches |
| Go | fetched at runtime — a Go module is a source tree, and bundling every platform would make each `go get` pull ~70 MB nobody uses |

In Go, download it once and point the loader at it:

```go
if _, err := modelnexus.Fetch(); err != nil { log.Fatal(err) }
chat, err := modelnexus.Open("model.gguf")   // the cache is searched automatically
```

You do not have to pass the path anywhere. Until 0.2.1 you did — `Fetch()` downloaded the
library, returned a directory, and the next `Open` still failed unless you fed it back through
`MODELNEXUS_LIB`. That was half a feature and it is fixed.

## Platforms

| platform | published | run |
|---|---|---|
| `darwin-aarch64` | yes | continuously |
| `linux-x86_64` | yes | continuously |
| `windows-x86_64` | yes | verified on real hardware, 0.2.1 |
| `windows-aarch64` | yes, since 0.2.1 | **both suites, natively** — Go 27 pass / JS 27 pass |
| `darwin-x86_64` | staged by hand | not in CI |

**Windows on ARM matters more than it sounds.** Every Copilot+ PC is one, and so is a Parallels
VM on an Apple Silicon Mac. Before 0.2.1 there was no usable path on that hardware at all: Node
is a native arm64 process and refuses an x64 DLL outright, and Go runs x64-emulated, so it
loaded the library and then died inside llama.cpp.

Intel macOS is staged by hand rather than built in CI — GitHub's Intel runners queue
indefinitely, and one job that never starts blocks the publish for every platform that did.

**On Windows the native is a single self-contained DLL.** llama, ggml and the C runtime are all
linked in, so there is nothing to install alongside it — no Visual C++ Redistributable, no
sibling libraries to keep together. 0.2.0 needed the redistributable and said so only by failing
with "The specified module could not be found", naming a file that was right there.

**The GPU is used by default** — every layer offloaded, Metal on macOS. Until 0.2.1 it was
hardcoded off for everyone: Metal would initialise, name your GPU, and then report
`offloaded 0/29 layers to GPU`. Pass `n_gpu_layers: 0` to get CPU-only back, which is worth
doing when you want a measurement that reproduces across machines.

No CUDA in the published builds.

Skip the step entirely and you get a typed error listing every path searched. Never a
segfault.

### MODELNEXUS_LIB

Point it at the library file, or the directory holding it. It wins over every other
candidate in all three bindings — use it for an air-gapped machine, a vendored copy, or
a build you made yourself.

```bash
git clone https://github.com/muthuishere/modelnexus && cd modelnexus
./core/build.sh                                  # downloads llama.cpp's prebuilt libs,
                                                 # compiles only our bridge — seconds
export MODELNEXUS_LIB=$PWD/core/dist/darwin-aarch64
```

`./core/build.sh --source` builds llama.cpp too, when you want the whole thing yourself.
On Windows use `core\build.cmd`, which defaults to source mode: llama.cpp's Windows
archive ships 29 DLLs and zero `.lib` import libraries, and MSVC cannot link a DLL
without one.

## A model

modelnexus loads GGUF, and only GGUF. Get one from Hugging Face — every popular open
model has a GGUF quantisation, and a 1.5B at `q4_k_m` is about 1 GB and runs on a laptop
CPU. These docs use `qwen2.5-1.5b-instruct-q4_k_m.gguf` throughout.

**One hard requirement: the model's chat template must support tool calling.** A model
without one is rejected at load rather than silently degraded. Check before you commit to
a multi-gigabyte download:

```go
info, err := modelnexus.Info("model.gguf")   // loads no context, creates no engine
fmt.Println(info.SupportsTools, info.ChatFormat)
```
</TabItem>
<TabItem label="Python">
