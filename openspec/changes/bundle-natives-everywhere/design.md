# Design — bundling the natives everywhere

Decision and rationale: [ADR-0010](../../../docs/adr/0010-bundle-the-natives-everywhere.md).
Evidence: [spike 0009](../../../spikes/0009-bundle-natives/).

This document covers the mechanics the ADR deliberately left out.

## The symlink manifest

`build.sh` stages `dist/<platform>/` with `cp -a`, preserving 18 symbolic links per platform,
because llama.cpp ships `libfoo.dylib -> libfoo.0.dylib -> libfoo.0.13.0.dylib` and
dereferencing them triples the largest library (`core/build.sh:125`).

`go:embed` walks with `fs.WalkDir` and takes regular files only. It does not record symlinks
and does not error about them. The bridge links `@rpath/libllama.0.dylib` — a symlink — so a
naive embed produces a closure that looks complete and cannot load.

The build therefore writes `links.json` into `dist/<platform>/`:

```json
{ "links": { "libllama.0.dylib": "libllama.0.0.9371.dylib",
             "libllama.dylib":   "libllama.0.dylib" } }
```

Two properties matter. It is **generated by the build that produced the closure**, so it
cannot drift from what shipped. And links may **chain** — `libggml.dylib -> libggml.0.dylib ->
libggml.0.13.0.dylib` — so replay order is irrelevant, because a symlink may legally point at
a name that does not exist yet and resolution happens at load time.

Windows has no symlinks in `dist/`, so the manifest is empty there. The code path is the same;
only the data differs.

## Extraction

Spike 0009's `extract/main.go` is the shape to reproduce properly:

- **Temp directory, then rename.** A killed process must never leave a half-extracted closure
  at the path a loader reads — the same rule the model downloader and the job bus already
  follow.
- **A `.complete` stamp** makes the second run free. Hashing 14 MB on every process start
  would cost more than the load it protects.
- **Cache directory keyed on a hash of the embedded bytes**, not on a version string. Keying
  on the llama.cpp tag alone already served a stale library once; `fetch.go` had to grow
  `BridgeVersion` to fix it. A content hash cannot have that bug.
- **Mode `0o755`** on extracted files. Some loaders care, and it is miserable to debug.
- **A lost `os.Rename` race is success**, not an error: the other process wrote identical
  bytes. Check the stamp before reporting failure.

Extraction target is the existing user cache root, honouring `MODELNEXUS_CACHE`.

## Why the Go bundle is a separate module

Go has no optional dependencies and `go:embed` selects at compile time, not fetch time. Five
platforms inside `bindings/go` is ~70 MB in every consumer's module cache, including consumers
who only ever set `MODELNEXUS_LIB`.

A build tag does not help. `source.go:199` already records why, for the S3 resolver: **a
tagged file's imports still land in `go.mod`**. Same constraint, same answer.

```
github.com/muthuishere/modelnexus/bindings/go        lean, unchanged
github.com/muthuishere/modelnexus/natives            ~70 MB, opt-in
```

The `natives` module embeds per platform behind build tags, so the *binary* carries only its
own platform even though the *module* carries all five. Its `init()` registers a resolver the
base binding consults at step 2 — the same hook shape as `RegisterScheme`.

### Considered: five separate per-platform modules

`natives-darwin-arm64`, `natives-linux-x86_64`, … would make the download 14 MB instead of 70.
Rejected: the consumer's import would have to be build-tag-gated in *their* code, and a
cross-compiling consumer would need several. That trades a one-line opt-in for a per-platform
chore, which is the friction this is meant to remove. Revisit if the module cache cost turns
out to bite in practice.

## Python and JavaScript

No packaging change — wheels and `optionalDependencies` already bundle correctly. Both gain
the steps they are missing from the resolution order:

- `MODELNEXUS_LIB` first (Python and JS currently ignore it)
- `core/dist/<platform>/` for in-tree work
- `Fetch()` last, ported from `fetch.go`, for a platform the distribution does not carry

That last one is what closes the Intel-Mac-shaped hole for any *future* unbuilt platform,
without moving the happy path off the wheel.

### Wheels dereference, and that is correct

Measured rather than assumed. Building the 0.2.1 wheel from a 14 MB staged closure:

```
wheel on disk : 14.1 MB
native entries: 31   symlinks: 0   uncompressed: 42.4 MB
```

setuptools copies package data with `shutil.copy`, which follows links, so all 18 become full
copies. **Download size is unaffected** — zip deflate re-compresses the duplicates — but
installed size is 3×, and this is the status quo, not something this change introduces.

It should stay that way. `pip` extracts wheels with `zipfile`, which does **not** restore
symlink entries: a link would install as a regular file whose *content* is the target's name,
producing a 25-byte "library". Dereferencing is the safe choice for wheels; the alternative is
broken, not merely large.

npm tarballs are a different matter — tar carries links natively — so the JS packages should
keep them, and that is worth verifying rather than assuming.

This is why the requirement is written as **name completeness** rather than link preservation.
The bridge resolves siblings by name at load time; whether a name is a link or a copy is an
efficiency question, and the ecosystems disagree about which is safe.

## darwin-x86_64

`build.sh` never compiles llama.cpp; it downloads upstream's `macos-x64` release dylibs and
compiles only the ~890-line bridge against them. So Intel macOS needs one flag, not a port:

```
cmake -DCMAKE_OSX_ARCHITECTURES=x86_64 …
```

`build.sh` gains `--platform <key>` to drive this, replacing the hand-seeding one-liner in
`PUBLISHING.md`. The matrix entry runs on `macos-latest` (arm64).

**Verification must load and generate, not inspect.** `lipo -archs` reporting `x86_64` is the
same weak claim that let three broken Windows natives ship green. The Windows ARM native
loaded cleanly and then died inside ggml's compute kernels. CI runs the cross-built native
under Rosetta and requires a correct token.

## Gate

The parity gate grows a resolution case: with `MODELNEXUS_LIB` unset and a bundled closure
present, every binding reports the same resolved directory and the same `Version()`, and makes
no network request. Without this, the ordered-steps requirement is three implementations of a
vibe.

## Open question

**Does the closure need to be extracted at all on Linux?** `dlopen` from a `memfd_create`
descriptor is possible there and would remove the filesystem dependency for that platform —
but only that platform, and a divergent load path is a poor trade for one OS. Left alone
deliberately; noted so it is not rediscovered as a bright idea later.
