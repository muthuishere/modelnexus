# Spike 0009 — bundling the natives everywhere

Evidence for ADR-0010. Two factual questions the decision depends on.

## Q1 — Can an Apple Silicon runner produce a working `darwin-x86_64` native?

**Why it matters.** `natives.yml:51` leaves Intel macOS out of the matrix because
GitHub's Intel runners queue 50+ minutes and one stuck job blocks every other
platform's publish. It is seeded by hand instead, which in practice means it is
absent — `natives-b9371` has four assets, not five. Bundling makes that hole
permanent rather than merely embarrassing, because a wheel with no library in it
fails at import, not at install.

**Method.** `cross-darwin-x64.sh` replays `core/build.sh`'s prebuilt path with one
addition, `-DCMAKE_OSX_ARCHITECTURES=x86_64`. Then `probe/` is built `GOARCH=amd64`
and run under Rosetta 2 — which makes an Apple Silicon Mac an honest Intel test bed.

The reason this is cheap is easy to miss: **the build never compiles llama.cpp.**
`build.sh` downloads llama.cpp's own `macos-x64` release dylibs and compiles only our
~890-line bridge against them. Cross-compiling Intel is therefore one clang
invocation, not a port.

```
==> cross-building darwin-x86_64 on arm64 | llama.cpp=b9371
==> upstream libllama arch: x86_64
==> bridge arch: x86_64

probe running as darwin/amd64
ok    loads    llamabridge 0.2.1 (llama.cpp b9371)
ok    generates Paris
```

Generation matters more than loading. The Windows ARM native loaded cleanly and then
died inside ggml's compute kernels with `0xC0000409`; only producing a token
exercises that path.

**Verdict: YES.** No Intel runner is needed. Build `darwin-x86_64` on `macos-latest`
and delete the manual seeding step from `PUBLISHING.md`. 13 MB, same shape as every
other platform.

## Q2 — Can Go embed the native closure, extract it, and load it?

**Verdict: YES, but not naively — `go:embed` silently destroys the closure.**

The hazard is not size. It is **symlinks**. `dist/darwin-aarch64` is 12 regular files
and **18 symlinks**, because llama.cpp ships `libfoo.dylib -> libfoo.0.dylib ->
libfoo.0.13.0.dylib` and `build.sh` preserves them with `cp -a` on purpose —
dereferencing turns one 7.5 MB library into three (`core/build.sh:125`).

`go:embed` walks with `fs.WalkDir` and takes regular files only. It does not record
symlinks and **does not error about them**:

```
on disk : 12 regular files, 18 symlinks
embedded: 12 entries
symlink names LOST by go:embed: 18
    libllama.0.dylib
    libggml-base.0.dylib
    ...
```

That is fatal, and quietly so. `otool -L libllamabridge.dylib` shows the bridge links
`@rpath/libllama.0.dylib` and `@rpath/libggml-base.0.dylib` — **versioned names, both
of which are symlinks.** A naive embed yields a directory that looks right, weighs
about right, and cannot load. It is the same class of failure as the three green
Windows builds that shipped a native nobody had ever loaded.

**The fix**: generate a `links.json` manifest at stage time and replay it on extract.

```
extracted: 14 regular files, 18 symlinks
idempotent: yes
ok    loads    llamabridge 0.2.1 (llama.cpp b9371)
ok    generates Paris
```

Rejected alternatives:

- **Dereference before embedding.** Correct and wasteful: ~14 MB becomes ~40 MB per
  platform. `build.sh` already refuses this for the same reason.
- **Reconstruct links by pattern at extract time** (`libfoo.dylib` is "probably" the
  newest `libfoo.N.dylib`). Guessing at a linker contract.

The manifest is generated by the build, so it cannot drift from what shipped.

**Extraction details that turned out to matter**, all in `extract/main.go`:

- Extract to a temp dir and **rename into place**. A killed process must never leave a
  half-extracted closure, because the next run would `dlopen` it. Same rule as the
  model downloader and the job bus.
- A `.complete` stamp makes the second run free — hashing 14 MB on every process start
  would cost more than the load it protects.
- Cache directory keyed on a **hash of the embedded bytes**, not on a version string.
  The downloaded-natives path already had to learn this once: keying on the llama.cpp
  tag alone silently served a stale library across a bridge change.
- Files written `0o755`. Some loaders care, and it is miserable to debug.
- A lost `os.Rename` race is a success, not an error — the other process wrote the
  identical bytes.

## Cost, stated plainly

~13–14 MB per platform. Five platforms is **~70 MB** in one Go module, downloaded by
everyone who imports it — which is why ADR-0010 puts it in a **separate, opt-in
module** rather than in `bindings/go`. Python and JS already bundle and pay nothing
new; a user downloads only their own platform's wheel or optional dependency.
